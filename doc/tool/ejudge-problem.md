# ejudge-problem

Навигация: [Система ejudge](../система_ejudge.md)/[Использование](../использование.md)/[Общая архитектура системы](../общая_архитектура_системы.md)/[ejudge-problem](ejudge-problem.md)

Эта утилита командной строки предназначена для подготовки задачи к использованию
в турнирах.

Поддерживается начиная с версии [3.14.0](../change/изменения_в_версии_3.14.0.md).

Утилита выполняет различные действия в соответствии со спецификацией задачи.
Спецификация задачи по умолчанию находится в файле `ejproblem.xml`
в формате XML. Схема XML-файла напоминает схему XML-файла `problem.xml`
для задач, сформированных в системе Polygon, и, возможно, для простых задач
совместима с форматом `problem.xml`.

Использование:

```bash
ejudge-problem [GLOBAL-OPTIONS]... TOOL [TOOL-OPTIONS]
```

Поддерживаются следующие подкоманды TOOL:

| Подкоманда | Краткое описание |
|------------|------------------|
| `print-hash` | Вывести на стандартный поток вывода SHA256 от всех исходных файлов задачи |
| `print-makefile` | Вывести на стандартный поток вывода условный Makefile, с помощью которого выполняются все действия по подготовке задачи |
| `print-source-files` | Вывести на стандартный поток вывода список исходных файлов задачи |
| `print-topological` | Вывести на стандартный поток вывода порядок сборки файлов задачи |
| `print-build-info` | Вывести на стандартный поток вывода информацию о сборке задачи |
| `normalize` | Выполнить нормализацию тестов |
| `build` | Выполнить сборку задачи |
| `clean` | Удалить все сгенерированные файлы |
| `zip` | Собрать архив задачи, содержащий только исходные файлы |

## Конфигурационный файл

Конфигурационный файл называется `ejproblem.xml` и описывает правила для
подготовки задачи к тестированию.

*Исходными файлами* считаются все файлы, упомянутые в `ejproblem.xml`,
которые не являются результатом сборки из других файлов, и сам файл `ejproblem.xml`.

*Целевыми файлами* считаются все файлы, упомянутые в `ejproblem.xml`
и являющиеся результатом сборки.

Все остальные файлы в каталоге задачи игнорируются.

Конфигурационный файл имеет следующую структуру:

* заголовок задачи
* описание файлов с условиями
* описание файлов с тестами
* описание дополнительных файлов
* описание правил сборки

### Заголовок задачи

Заголовок задачи имеет следующий вид.

```xml
<?xml version="1.0" encoding="utf-8" standalone="no"?>
<problem short-name="NAME" uuid-from-history="BOOL-VALUE">
    <names>
        <name language="russian" value="RUSSIAN-NAME"/>
        <name language="english" value="ENGLISH-NAME"/>
    </names>
    <!-- описание файлов с условиями -->
    <!-- описание файлов с тестами -->
    <!-- описание дополнительных файлов -->
    <!-- описание правил сборки -->
</problem>
```

Атрибут `short-name` задаёт короткое имя для задачи, соответствует
параметру [`short_name`](../serve.cfg/problem/short_name.md).
Атрибут `uuid-from-history` задаёт флаг, что GUID задачи для сохранения
в базе данных посылок должен браться из файла history.txt, находящегося
в каталоге задачи. Значение по умолчанию &mdash; `false`. В конфигурационных
файлах турнира ему соответствует параметр
[`enable_problem_history`](../serve.cfg/global/enable_problem_history.md).

В элементе `name` задаются длинные названия задачи на разных языках.
Элемент `name` соответствует параметру [`long_name`](../serve.cfg/problem/long_name.md).

### Описание файлов с условиями

Файлы с условиями перечисляются в элементе `statements`. Каждый файл описывается элементом `statement`. Этот
элемент не должен иметь тело и может иметь следующие атрибуты:

| Атрибут | Тип значения | Описание |
| - | - | - |
| `charset` | string | кодировка файла с условием, если файл текстовый. Поддерживается значение `UTF-8`. |
| `language` | string | язык, на котором написано условие (`russian`, `english`...) |
| `mathjax` | boolean | если `true`, в файле есть TeX-формулы для рендеринга с помощью MathJax |
| `path` | string | путь к файлу с условием в каталоге задачи |
| `type` | string | тип файла |

Поддерживаются следующие типы файла

| Тип | Описание |
| - | - |
| `application/x-ejudge-xml` | файл с условием в формате [ejudge XML](../statement.xml.md), см. [`xml_file`](../serve.cfg/problem/xml_file.md) |
| `text/markdown` | файл с условием в формате markdown, см. [`md_file`](../serve.cfg/problem/md_file.md) |

Пример.

```xml
    <statements>
        <statement charset="UTF-8" language="russian" mathjax="true" path="statement.xml" type="application/x-ejudge-xml"/>
        <statement charset="UTF-8" language="russian" path="statement.md" type="text/markdown"/>
    </statements>
```

### Описание файлов с тестами

Описание файлов с тестами находится в элементе `judging`.

Атрибуты элемента `judging` перечислены ниже.

| Атрибут | Тип значения | Описание |
| - | - | - |
| `extra-config` | `boolean` | Если равен `true`, то дополнительные параметры настройки задачи задаются в файле problem.cfg в каталоге задачи. Файл problem.cfg содержит конфигурационные
параметры задачи, которые копируются в [секцию задачи](../serve.cfg/problem.md) |

В элементе `judging` должен находиться единственный элемент `testset`, который
задаёт набор тестов для тестирования. Множественные вхождения `testset`
в настоящее время не поддерживаются.

Элемент `testset` может иметь следующие атрибуты:

| Атрибут | Тип значения | Описание |
| - | - | - |
| `name` | `string` | название тестового набора &mdash; игнорируется |
| `generate-answer` | `boolean` | если равен `true`, файлы с эталонным ответом автоматически генерируются с помощью эталонного решения |
| `auto-count` | `boolean` | если равен `true`, количество тестов к задаче автоматически определяется по числу файлов с исходными данными. Этот атрибут может быть полезен, когда в тестовых данных нет генерируемых тестов |
| `normalization` | `string` | требует, чтобы все тестовые данные были в определённом формате концов строк. См. параметр задачи [`normalization`](../serve.cfg/problem/normalization.md) |

Внутри элемента `testset` находятся элементы, описывающие тестовый набор.

Элемент `input-path-pattern` задаёт шаблон имени файла со входными данными.
В секции конфигурации задачи конфигурационного файла ему соответствует
параметр [`test_pat`](../serve.cfg/problem/test_pat.md).

Элемент `input-path-pattern` может иметь следующие атрибуты:

| Атрибут | Тип значения | Описание |
| - | - | - |
| `binary` | `boolean` | входные данные &mdash; бинарные, к ним не применяются нормализации |

Элемент `answer-path-pattern` задаёт шаблон имени файла с эталонным ответом.
В секции конфигурации задачи конфигурационного файла ему соответствует
параметр [`corr_pat`](../serve.cfg/problem/corr_pat.md).

Элемент `output-path-pattern` может иметь следующие атрибуты:

| Атрибут | Тип значения | Описание |
| - | - | - |
| `binary` | `boolean` | результат работы имеет бинарный формат, к нему не применяются нормализации |

В элементе `tests` перечисляются тесты в данном тестовом наборе. Внутри элемента `tests`
должны находиться только элементы `test`, описывающие каждый тест в тестовом наборе.
Нумерация тестов неявная, начинается от 1.

Элемент `test` не должен содержать вложенных элементов.
Для элемента `test` поддерживаются следующие атрибуты.

| Атрибут | Тип значения | Описание |
| - | - | - |
| `method` | `string` | если значение `manual`, файл с тестовыми данными формируется вручную и должен существовать, а если значение `generated`, то файл с тестовыми данными должен быть сгененирован с помощью программы-генератора. |
| `sample` | `boolean` | если значение `true`, данный тест является "тестом из условия" |
| `cmd` | `string` | для тестов со значением `method=generated` атрибут `cmd` позволяет задать команду для генерации файла со входными данными |

Пример.

```xml
    <judging extra-config="true">
        <testset name="tests" generate-answer="true" auto-count="true" normalization="">
            <input-path-pattern>tests/%03d.dat</input-path-pattern>
            <answer-path-pattern>tests/%03d.ans</answer-path-pattern>
            <tests>
                <test method="manual" sample="true"/>
                <test method="manual" />
                <test method="manual" />
                <test method="generated" cmd="gen 1 2 3" />
                <test method="generated" cmd="gen 1 2 4" />
            </tests>
        </testset>
    </judging>
```

### Описание дополнительных файлов

Дополнительные файлы &mdash; это файлы, непосредственно не требующиеся для
проверки решений в ejudge, но которые желательно включить в список
"исходных" файлов для задачи, по которым будет вычисляться контрольная сумма.

Дополнительные файлы задаются в элементе `files`, в который должен быть
вложен элемент `resources`, в котором находится список элементов `file`
с путями к файлам, как показано на примере.

Пример.

```xml
    <files>
        <resources>
            <file path=".gitignore" />
            <file path="history.txt" />
            <file path="problem.cfg" />
            <file path=".clang-format" />
        </resources>
    </files>
```

### Описание правил сборки

В этом разделе описываются правила для сборки эталонных решений,
проверяющих программ, генераторов и т. п. Правила для сборки находятся
в элементе `assets`. В элемент `assets` вложены элементы, описывающие правила
сборки для конкретных типов программ.

* Дополнительные файлы для компиляции решения находятся в элементе `solution-files`.
* Правила сборки решений находятся в элементе `solutions`.
* Правила сборки генераторов находятся в элементе `generators`.

#### Дополнительные файлы для решения

В этом разделе перечисляются файлы header/footer, которые текстуально добавляются
к файлу с решением перед компиляцией файла с решением.

```
        <solution-files>
            <solution-file type="header" path="header.c" />
            <solution-file type="footer" path="footer.c" />
        </solution-files>
```

Типу `header` соответствует конфигурационный параметр задачи [`source_header`](../serve.cfg/problem/source_header.md).

Типу `footer` соответствует конфигурационный параметр задачи [`source_footer`](../serve.cfg/problem/source_footer.md).

Оба элемента опциональны.

#### Пример описания правил сборки

Пример.

```xml
    <assets>
        <solutions>
            <solution tag="main">
                <source path="solution.c" />
            </solution>
        </solutions>
        <generators>
            <generator>
                <source path="gen.cpp" />
            </generator>
        </generators>
    </assets>
```
